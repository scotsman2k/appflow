# AppFlow: Live AWS Architecture Explorer

An organization-neutral, interactive architecture dashboard that visualizes requests through an **existing** Application Load Balancer (ALB), EC2 Auto Scaling group, PostgreSQL database and Amazon S3. Each request names the exact EC2 instance that responded. When enabled, the same instance runs read-only PostgreSQL and S3 connectivity checks. Results drive animated flow paths and the event stream.

**No Terraform, CloudFormation, account vending, AWS resource creation or credentials are included.** AppFlow installs beside an existing web application. Its routes are mounted into the web server already serving the existing ALB target group. **Client-facing traffic uses HTTPS port 443. The expected existing path is ALB HTTPS:443 → target group HTTPS:443 → EC2 web server TLS:443 → local Node adapter 127.0.0.1:8787.** The loopback adapter port is not a browser-facing endpoint.

## What is live, and what is not

| UI signal | Evidence | Boundary |
| --- | --- | --- |
| Page served by EC2 | The page-rendering backend reads its identity through IMDSv2 | Only the page's initial responder |
| User → ALB → EC2 animation | The `/api/demo/request` JSON names the actual responding EC2 instance and request ID | Only requests generated by this browser, not all ALB traffic |
| EC2 membership, names, AZs and target health | Read-only Auto Scaling, EC2 and ELBv2 Describe calls | Inventory and health snapshots, refreshed every 30 seconds |
| EC2 → RDS animation | Read-only `SELECT 1` through a certificate-verified PostgreSQL TLS session | A successful query from the responding EC2, not business-data integrity |
| EC2 → S3 animation | `HeadObject` for an existing sentinel object | Object read-path access only, not write access or replication completion |
| S3 replica label | Runtime configuration | No replication success is claimed without independent verification |

The local-test mode is labeled **LOCAL TEST** and intentionally calls neither AWS nor the dependencies. The visual simulation's scale/failure buttons are disabled in all adapter modes. **The dashboard never scales instances or changes AWS resources.**

## Repository map

- `dashboard/`: self-contained SVG visualization, styles, event stream, inspector and animation.
- `backend/`: Node.js 20+ HTTP adapter, AWS inventory, EC2 identity and opt-in dependency probes.
- `deploy/`: application-only release and install scripts, service unit, reverse-proxy *snippets for an existing web server*.
- `tests/`: Node integration tests and an internal ALB smoke test.
- `docs/EXISTING_STACK_RUNBOOK.md`: application deployment, discovery, troubleshooting and rollback.
- `docs/CLAUDE_CODE_HANDOFF.md`: precise instructions and acceptance criteria for a coding harness.
- `docs/VALIDATION_MATRIX.md`: proof points, commands, and honest interpretation.
- `docs/PUBLIC_RELEASE_SAFETY.md`: public source versus private live deployment boundary.

## Start locally without AWS

```bash
cd backend
npm ci --omit=dev --ignore-scripts
npm test
APP_MODE=local-test npm start
```

Open `http://127.0.0.1:8787/dashboard/`. The backend is bound to **127.0.0.1 only**. Expected fake identity: `i-local-test`; RDS/S3 probe routes are disabled. This is functional smoke testing, not AWS validation.

## Wire into an existing EC2 application

- Identify the running ASG, target group, ALB, existing HTTPS origin and web-server process. Confirm they belong to the same pre-deployed application.
- Build the application-only archive using `bash deploy/build-release.sh`; distribute via the approved existing software release path.
- Put a **runtime-only** config at `/etc/architecture-dashboard/dashboard.env` using `backend/.env.example`. Keep actual resource identifiers, secrets and endpoint names out of the public Git repository. A Secrets Manager ARN references an **existing** secret; it is not a password.
- On **every** EC2 member, install the archive with `bash deploy/install-on-ec2.sh /path/unpacked --check` followed by `--apply` once reviewed. This affects only the dashboard service. It never overwrites existing Nginx or Apache configuration.
- Verify the already deployed target group speaks **HTTPS on port 443** to the EC2 web server. If it does not, report the mismatch; this application does not change load balancer configuration.
- In the existing HTTPS **port 443** virtual host, proxy `/dashboard/` and `/api/demo/` to `http://127.0.0.1:8787`, retaining existing authentication and TLS policies. See the templates under `deploy/`. **Do not create a listener, target group, security group or ALB for this application.**
- Validate on the local host and through the existing internal ALB, then incorporate the application into the already approved instance image/user-data/release automation so replacement EC2 instances run the same code.

The existing ALB health check remains unchanged. The application exposes additional read-only endpoints at `/api/demo/health` and `/api/demo/ready`.

## Runtime requirements

| Setting | Purpose |
| --- | --- |
| `APP_MODE=live` | Actual EC2 identity and AWS discovery, never fake data |
| `AWS_REGION` | Region of existing ASG, ALB and RDS |
| `ASG_NAME` and `TARGET_GROUP_ARN` | Existing fleet and target health, required in live mode |
| `ALB_NAME`, `RDS_IDENTIFIER` | Optional names used for richer inventory |
| `ENABLE_DEMO_PROBES` | Start with `false`; only enable after confirming existing access paths |
| `DB_HOST`, `DB_NAME`, `DB_SECRET_ARN`, `RDS_CA_BUNDLE` | Existing DB endpoint, read-only user reference and CA; required for enabled probes |
| `S3_BUCKET`, `S3_SENTINEL_KEY`, `S3_REPLICA_BUCKET` | Existing source bucket/object and optional replica label |
| `DASHBOARD_PORT` | Loopback HTTP port, default `8787` |

The existing EC2 instance role must already allow the necessary Describe, `s3:GetObject`, and optional `secretsmanager:GetSecretValue`/KMS operations, including applicable endpoint/bucket/key policies. This repository does not define or attach IAM policies. RDS uses TLS with server verification and `SELECT 1`; the PostgreSQL identity must not have administrative privileges.

## Validate

```bash
# From approved internal network access to the existing HTTPS origin:
BASE_URL=https://existing-application.example.internal EXPECT_MIN_INSTANCES=2 bash tests/smoke.sh

# Only after both real dependency checks are enabled and verified:
BASE_URL=https://existing-application.example.internal EXPECT_PROBES=true bash tests/smoke.sh
```

The second command makes real requests to the existing RDS and S3 endpoints. Use judicious traffic volume; don't load-test a production system through this demo. For two or more instances, the 30-request sample demonstrates possible distribution but does **not** guarantee equal balancing or reachability of every target.

## Security and publication

The repository contains only source code, generic examples and mock identifiers. No credentials, certificates, real account IDs, internal hostnames or organization branding should be committed. AppFlow's live endpoints can expose private resource identifiers and dependency states: deploy only behind an **existing authenticated internal application origin**. Public demonstrations should use `APP_MODE=local-test` or a static synthetic preview.

There is no deployment to an AWS account in this repository; all environment-specific validation must be performed in the authorized account. See `docs/EXISTING_STACK_RUNBOOK.md` for required proof and rollback.
